## Details

**D-1.** The Linear wording "keep the current UI" is leftover from before the 4 Nov meeting. Nothing to preserve.

**D-2.** Order: scaffold, REC-25 (flags, day-limit control, error state), REC-27 (vehicle detail and decision form), REC-26 (history, which needs decisions to exist to be useful), REC-28 (PDF, needs all three views), then REC-12 (deck, which uses figures from the finished app and the seed-42 data).

**D-3.** Add a small static-file route to `recall_tracker/api.py` (stdlib only) and put the UI in `ui/` as plain HTML, CSS and JS with no build step. One origin means no CORS, one command (`serve`) runs everything, and there is no Node toolchain for a small app. Constraint: serve only files under `ui/` (no path traversal), GET only, no new write operation. This keeps the "no owner-contact, source-edit or automatic-decision operation" rule intact. Trade-off: it touches a file the check-engine owner wrote, so the team reviews that change (D-13). The alternative (separate dev server plus proxy) adds tooling for no gain at this size.

**D-4.** Every day-limit change saves a new run (`POST /api/day-limit`). Accepted because the client has not shared real data volumes. Revisit when they do.

**D-5.** Filters, all client-side over the `history` and `decisions` arrays (no API change). The coordinator's questions are "what still needs my attention?" and "what happened to this vehicle?", so:
- Search by VIN (partial match).
- Campaign id.
- Kind: notification, repair, data quality.
- Check date range.
- Current decision: reviewed, follow up, no action, or no decision yet.
- Day limit used.
Defaults: newest first, no ranking between notification and repair. Include a "clear filters" control and a visible count of matching rows.

**D-6.** `decided_on` is the date stored on a decision. The API defaults it to today when omitted (`api.py:130`). "Current" is chosen by the latest `decided_on`, then by recording order (`contract/decision.py:61-70`). If the UI let a user pick a past date, a newly saved decision could lose to an older one and not become current. So the UI omits the field.

**D-7.** Ingest flags later rows with different dates as `DATE_CONFLICT` and keeps them (`ingest.py:325-336`). The check uses the earliest notice (`contract/days.py:36-43`) and the earliest repair on or after it (`days.py:46-59`). On the detail screen show: the date used (labelled), any other notice dates from `facts.notices`, and the reason from `data_quality_reasons`. Source row numbers are only in the matching `data_issues` entry, so link to it rather than adding an API field.

**D-8.** `raw_row` can contain a hostile `tech_note`. Show it only inside an expandable element, rendered with `textContent` (never `innerHTML`). The data-issue list also gets file and issue-code filters (not built so far; the list scrolls and is small, so this stays open).

**D-9.** On HTTP 422 the screen shows the `error` text and nothing else in the findings area: no empty list, no older findings next to the error. Matches REC-25 and the client decision of 4 Nov.

**D-10.** Use `window.print()` with a print stylesheet. No dependency. Revisit only if a downloadable file endpoint becomes a requirement.

**D-11.** Three team members present, 15 minutes, no branding. Use real counts from a seed-42 run (as-of 2026-11-01) since the client shared no figures.

**D-12.** `docs/plan.md` was initial-phase planning. Do not update it. Rely on Linear, the code, and `docs/architecture/overview.md`.

**D-16.** Sanket creates the branch (Linear's suggested name, for example `meetsanket24/rec-25-show-notification-repair-and-data`) and raises the PR. Before editing, Claude runs `git status` and `git branch --show-current` and stops if the branch does not match the ticket. Before handing off, Claude checks that every planned change for the ticket is done and the tests pass, then lists the files changed. Planned order: REC-25, REC-27, REC-26, REC-28, REC-12. Branches are stacked because approvals may be slow: branch 1 from `main`, branch 2 from branch 1, branch 3 from branch 2, and so on. Each PR's base is the previous branch (so its diff shows only that ticket); merge in order and retarget each PR to `main` once its parent merges. Prefer regular merge commits over squash for the stack (squash makes the next branch conflict). Before merging a branch to `main`, Sanket pulls the latest `main` into it and resolves conflicts locally. A review fix goes on the branch it belongs to, then Sanket merges or rebases it forward into each later branch. Claude names the parent branch when each ticket starts and reminds which later branches need updating after a fix.

**D-18.** Refines D-9. A 422 (unusable file) hides every finding and shows only the error. A 400 on first load means no check has run yet ("No check has been run yet"). Other failures, such as a rejected day limit, show a message and leave the current report on screen so a typo does not wipe the page. Client-side validation (day limit must be a whole number of 1 or more) uses the same message box.

**D-19.** Added on the REC-25 branch beyond the ticket text: four summary cards (notification, repair, data issues, data-quality flags; notification and repair equal weight), a "Run check" button (needed so a first check and the 422 error can be triggered from the UI), and tables that scroll inside a 520px box with sticky headers. The data-issue table merges file and row, and code and action, to avoid sideways scrolling.

**D-20.** REC-27 details. The detail view is a hash route (`#/vehicle/<vin>/<campaign>`), so it needs no new server route and the browser Back button works. VINs in the findings, data-quality and (when the pair is in the report) data-issue tables are links to it. It shows the check's inputs (in notices file, notice and repair date used, day count, limit, on time or late), the notification and repair findings, all dates on file with the used ones marked, data problems (kept apart and de-duplicated by wording), the current decision, a form, and the decision history (newest first). With no repair on file the day count is labelled "Days since notice" and counted to the check date, because that is what the contract returns (`inclusive_days` to the check date, `on_time` null). The form posts `vin`, `campaign_id`, `status` and an optional `note`, and reloads `/api/report` (no new check run). It does not send `decided_on` (D-6).

**D-21.** Reviewer comment on the REC-25 PR: after a file error, reloading or pressing Apply brings back the last good report with no warning, and Apply saves a new run while a file is missing. Cause: a failed check writes nothing, so the last good ingest stays current, and `recheck` (reload and Apply) works on loaded data without re-reading the CSVs. Fix: every run payload from the API carries `loaded_at` (the ingest's `finished_at`, UTC ISO text, added beside `report` so the contract shape is unchanged) and the header reads "Data loaded from files on <local time> · check date … · run … · repair limit …". Applying a day limit still does not re-read the CSVs. Not done: making Apply refuse when a CSV is missing (it would change the rule that recheck uses loaded data). The fix went onto the REC-27 branch because the REC-25 PR was already merged.

**D-22.** REC-26 details. The history view is the hash route `#/history`, reached from a "Check history" link beside "Flags". It is read-only and built from the loaded report (`history`, `decisions`) plus `GET /api/runs`, so no API change. Sections: saved runs (run, check date, day limit, ingest), every saved check (check date, VIN link, campaign, kind, reason, day limit, current decision) newest first, and every coordinator decision (newest first, notes as plain text). Filters from D-5: VIN contains, campaign, kind, check date range, current decision (including "No decision yet"), day limit used, plus "Clear filters" and a count. The VIN and campaign filters also narrow the decisions table; the other filters only apply to checks. At most 500 check rows show; the count says how many match. Notification and repair are shown with equal weight. The `history` payload has no run id, so a check row cannot be tied to its run except through its check date and day limit; adding it needs a contract change and was not done. "Current decision" uses the same rule as the server (latest `decided_on`, then later record).

**D-23.** REC-28 details. "Export PDF" opens a dialog where the person chooses what to include: findings, missing and bad data, vehicle detail, saved runs, every saved check, coordinator decisions. Every part is on except "every saved check" (the long one: 932 rows after 3 runs). The summary at the top is always included. The choice is remembered until the page reloads. The PDF says which parts were left out, so a partial export is not mistaken for the whole report. Then `buildPrintReport` fills `#print-report` (print-only, hidden on screen, A4 landscape) and calls `window.print()`; the person chooses "Save as PDF". The page title is set to "Recall report <check date> run <n>" while printing so the file gets a useful name. Look: a cover band with dealership, check date, run, day limit and load time; five large number cards (vehicles checked per campaign, notification, repair, data issues, data-quality flags; notification and repair equal); a footer with page numbers; "Missing and bad data" in its own purple section. Vehicle detail covers every vehicle with a finding, a flag or a decision. The data-issue `raw_row` is left out (it can hold a hostile `tech_note` and is collapsed on screen); everything else uses `textContent`. The button is disabled when no report is loaded, so a PDF can never be made after a file error (422). Size with seed-42 data and 3 saved runs: about 47 pages by default, about 105 with every saved check.

**D-24.** Reviewer comment on REC-27. (1) A vehicle that has a notice or repair row but is not on the affected list showed "197 days, limit 60, no repair" with no finding, which reads as overdue. The detail page now starts with an "In affected list" fact. When it is "No", the day count is hidden, the result reads "Not applicable (not in the affected list)", and the PDF vehicle table leaves its Days cell empty (and gains an "In affected list" column). The check itself is unchanged: such a vehicle only has the data-quality flag. (2) Dates appeared in three styles. Facts use ISO (2026-07-18), the server's data-problem wording uses MM/DD/YYYY, and the header used the browser's locale. Now the header shows the load time in ISO style in the viewer's own time zone, with the generic zone name (for example "2026-11-08 17:35 ET"; client and team are in ET, so UTC was changed to local, and ET is used instead of EST/EDT so daylight saving never makes it look wrong), and `isoDates` in `app.js` rewrites real MM/DD/YYYY dates in reason text to ISO when displayed. A value that is not a real date (13/01/2026, 02/30/2026) is left as written, because it is the problem being reported. The server wording and the saved reports are not changed; the raw row text is not rewritten.

**D-25.** UI tests live in `tests/test_ui.py` and add no dependency (no Node packages, no browser driver). Source checks always run: no HTML built from API data (comments are ignored), no inline script, style or handler (the server's content security policy would block them), every element the script looks up exists, linked files are served, only the documented POST routes are used and no `decided_on` is sent, CSS braces balance, and `node --check` if Node exists. Browser checks start the real server over a checked copy of the seed-7 data, open it in headless Chrome with `--dump-dom --virtual-time-budget` and a fixed time zone (ET), and compare the rendered page with `/api/report`: row counts, header, day 60 and 61 pages, no day count outside the affected list, bad-date and no-repair cases, ISO dates, the history view, the first-run message and the export button state. They skip when Chrome is missing and run on GitHub's Ubuntu runners, which include Chrome. Not covered: clicks (saving a decision, the export dialog and print output, a 422 after "Run check"). Covering those needs a driver (Chrome DevTools from Node 22+, or Playwright), which adds a dependency; it was left out on purpose. Each new UI bug fix should add a test here. I confirmed the tests fail when the UI is broken four ways (day count for unaffected vehicles, `innerHTML`, a renamed element id, US dates left unconverted).

**D-26.** Reviewer finding on REC-28: an old report could still be exported after a file error, (1) after a reload or Apply, because the last good data comes back and the PDF looks current, and (2) with Ctrl+P on the error screen, because `showError()` left `#print-report` filled from an earlier export. Fixes, built test-first: (2) `clearPrintCopy()` runs in `render`, `showError` and `showNoCheckYet`. (1) The server cannot remember a failed check (it writes nothing), so every run response and `GET /api/report` now carries `input_check`, computed by `pipeline.input_check` by hashing the three CSVs and comparing with the hashes stored for the loaded ingest. `unusable` (a file is missing or unreadable now): a warning banner says it is the last good report, and Export PDF is disabled, which keeps the stop rule. `changed` (a file was edited after the load): the banner says the report is from the earlier data, and the PDF cover carries the same warning. A saved run (`/api/runs/<id>`) has no `input_check`. Not changed: the day-limit Apply still works on loaded data and still saves a run while a file is missing (the CLI `recheck` is documented to work without the CSVs); it now shows the warning instead. If the coordinator should be blocked from Apply too, that is a separate decision.
